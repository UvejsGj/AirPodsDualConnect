# Stage 2 proof-of-concept routes (desk research)

Oct 8, 2026 · @Uvejs Gjelaj

This is desk research, prepared while Stage 1 waits on your trials. Nothing in it has been run or changed on your laptop, and it is shelved if Stage 1 shows manual switching is good enough. Nothing here is tested on your exact setup (iPhone, Windows laptop, AirPods Pro 3, firmware 9A348).

## Summary

If Stage 1 fails its gate, run Stage 2 on a spare Realtek dongle driven by Google's Bumble from Python on Windows (Route A). It answers all three Stage 2 questions with no Test Mode, no Secure Boot change, no registry edit and no new kernel code; the only system change is Microsoft's WinUSB driver on the dongle, undone in five steps below.

- **Most of the code exists.** LibrePods already has a Windows script that opens Apple's channel through Bumble with an Apple identity scoped to the dongle, and Bumble ships an A2DP player. The missing piece is porting LibrePods' takeover messages from Rust into one Python script.
- **Stage 2A becomes optional.** Route A tests the Apple identity per run on the dongle, so the system-wide registry change no longer earns its risk.
- **Fallback:** the plan's Linux live-USB test (Route C1) runs LibrePods' complete code with the same dongle and changes nothing on the Windows disk.
- **Ruled out here:** NTPods' driver (2C), MagicPods and any virtual audio driver, since each puts kernel code on the laptop.
- **Worth having whatever Stage 1 shows:** a one-key "take" and "give back" that uses the same call as Windows' Settings (Route B1), with no driver or registry change.
- **One Stage 3 catch:** Route A has no user-mode way to give Windows the AirPods' microphone. A small Linux board acting as a USB headset (Route C2) would, and Stage 2's answers carry over to it.

## Route A: spare dongle with Bumble on Windows (recommended)

This is the route you named, and it can answer all three Stage 2 questions with no Test Mode, no Secure Boot change, no registry edit and no new kernel code. Its one system change is binding Microsoft's generic WinUSB driver to the spare dongle only. Everything in this section is plan and inference, untested on your setup.

### What it needs

- **A spare dongle Bumble supports.** A Realtek RTL8761B dongle is the safe pick, since Bumble lists its IDs and loads its firmware. TP-Link's UB500 is commonly reported as 2357:0604, one of those IDs; check the ID on the box or in Device Manager before relying on it. Avoid an Intel dongle if your built-in adapter is Intel (ID 8087:xxxx), so the two can't be confused. airlow's code does not fit a Realtek dongle, because it skips dongles that need firmware loading.
- **The dongle's firmware, loaded into its RAM.** Bumble's `bumble-rtk-fw-download` fetches the Realtek files, and Bumble loads them each time it starts, as Windows' own Realtek driver does. Nothing is flashed, and this has nothing to do with the AirPods' firmware.
- **Python 3.10 or later and Bumble** in a virtual environment in one folder.
- **LibrePods' Windows script** as the starting point: it already opens Apple's channel from Bumble with an Apple Device ID record.

### The one system change: WinUSB on the dongle

**What it does.** Windows stops treating the dongle as a Bluetooth radio and hands it to winusb.sys, Microsoft's generic USB driver that ships with Windows, so Python can drive the radio directly. Your built-in adapter, Windows' pairing with the AirPods and the iPhone's pairing are not touched. No new kernel code is installed.

**What else Zadig adds.** One self-signed certificate in the machine's Trusted Root and Trusted Publisher stores. libwdi deletes its private key after signing, so nothing new can be signed with it, but it is still a trust-store change and the undo removes it. Zadig needs administrator rights once.

**How it would be done (later, not now).**

1. Plug in the dongle. Windows may install it as a Bluetooth adapter; since Windows supports one radio, bind it before using Bluetooth again.
2. In Device Manager, open the dongle's Properties, Details, Hardware Ids, and note its VID and PID. Note the built-in adapter's too.
3. In Zadig, choose Options, List All Devices, select the entry whose USB ID matches the dongle (never the built-in one), pick WinUSB and click Replace Driver.
4. Check that the dongle now sits under "Universal Serial Bus devices", the built-in adapter is still under "Bluetooth", and the AirPods still connect to Windows as before.

**Exact undo.**

1. Device Manager, View, Devices by type, Universal Serial Bus devices: right-click the dongle, Uninstall device, tick "Attempt to remove the driver for this device" (Windows 10 words it "Delete the driver software for this device"), then Uninstall.
2. Unplug the dongle. If you plug it in again, Windows gives it its Bluetooth driver back.
3. In an administrator terminal run `pnputil /enum-drivers`. If an entry with Provider Name "libwdi" remains, run `pnputil /delete-driver oemNN.inf /uninstall` with its oem number.
4. Run `certlm.msc`. Under Trusted Root Certification Authorities, Certificates, delete each "USB\\VID\_…&PID\_… (libwdi autogenerated)" entry. Do the same under Trusted Publishers, Certificates.
5. Delete the test folder, which holds Bumble's `keys.json` (the dongle's link key for the AirPods), and uninstall Python if you added it only for this.

One thing stays behind: the AirPods keep a pairing record for the dongle's address. That should not affect the iPhone or Windows pairings, and nothing in this plan removes it by resetting the AirPods.

**Untested alternative without the certificate.** Microsoft documents choosing its in-box "WinUsb Device" by hand. Device Manager may not offer that class for a device it already treats as Bluetooth, and libusb may not open a device set up this way, so treat it as a first try with Zadig as the fallback.

### What it can measure

| Stage 2 question | How Route A answers it | New code |
| --- | --- | --- |
| Do both links hold for ten minutes? | iPhone connected first, then the dongle opens Apple's channel as LibrePods' script does. Log every connected-devices (0x2E) and audio-source (0x0E) packet with a timestamp. | Timestamped logging added to the script, a few dozen lines |
| Does the link survive the 40-second drop on 9A348? | Run the same session with the Apple Device ID record and without it, and time any disconnects. LibrePods says the AirPods cache the Device ID, so re-pair the dongle between runs: one pairing-mode double-tap, never a reset. | A flag to leave the record out |
| Does a takeover move the audio? | One Python process combines bumble-player's A2DP source with the Rust takeover messages: play a pre-encoded SBC file, send "Owns connection" and "Hijackv2", and note by ear and in the log whether sound moves and what the iPhone shows. | Port of three message builders from Rust, roughly 150 to 300 lines |

It has to be one process because only one application can hold a WinUSB device at a time ([libusb wiki](https://github.com/libusb/libusb/wiki/Windows)).

### Limits and precautions (inference)

- **Keep the built-in adapter out of the test.** The AirPods hold two hosts, so turn Windows' Bluetooth off in Quick Settings during runs. That switch no longer reaches the dongle once it is on WinUSB. Turn it back on afterwards.
- **Name the dongle explicitly.** Use `usb:2357:0604` (or your dongle's ID) rather than LibrePods' `usb:0`, so Bumble never reaches for the built-in adapter.
- **End every session with a clean disconnect.** airlow saw AirPods Pro 2 loop on reconnects after a controller reset. If that happens, put the AirPods in the case and close the lid, which is normal use and not a reset.
- **The test audio is a file, not Windows' sound.** In daily use, PC audio would reach the dongle by loopback capture, as airlow does. I know of no user-mode way to give Windows a microphone from the AirPods on this route, so laptop calls would need a kernel audio driver, which is ruled out, or Route C. This matters for the Stage 3 design, not for Stage 2.
- **Rough effort.** 2 to 3 hours for binding and a first link test, half a day for the logger, and 1 to 2 days for the takeover script.

## Route B: Windows' own Bluetooth, no dongle

Two options need no dongle and no driver. Neither gives a second live link under your control, but the first is the cheapest upgrade to the Stage 1 fallback, whichever way the gate goes.

### B1. One-key connect and disconnect

**Verified.** Microsoft documents [KSPROPERTY\_ONESHOT\_RECONNECT](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/ksproperty-oneshot-reconnect) as asking the Bluetooth audio driver to connect; success means an attempt was made, not that it worked. [ToothTray](https://github.com/m2jean/ToothTray) (commit 0d1a7ee, 15 Aug 2025) sends it, and its disconnect twin, from an ordinary tray app through Core Audio, which its README says is how Windows' Settings does it.

**Inference, untested.** A "take" key sends reconnect and a "give back" key sends disconnect. That needs no driver, no registry change and, as far as the code shows, no administrator rights. It is the reconnect hotkey the Stage 1 plan mentions, and Stage 1's S3 and S5 trials time the same actions done by hand. It could be a small feature in BatteryHub. Undo is closing and deleting the app.

### B2. Stage 2A registry identity test (now optional)

**What it is.** Setting `DIDVendorID` to `0x4C`, with `DIDVendorIDSource` `0x01` (Bluetooth SIG), under `HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters`. Microsoft's [defaults](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-host-radio-support) are source `0x01`, vendor `0x06` (Microsoft), product `0x01` and version `0x0800`.

**Why it drops to optional.** Route A asks the same question, whether an Apple identity changes the AirPods' behaviour, with the record limited to the dongle and switchable per run without a reboot. 2A's system-wide answer only matters for a design that opens Apple's channel through Windows' own stack, which needs a kernel driver and is ruled out here. The one thing only 2A shows is whether Windows' own link holds more often beside the iPhone, and LibrePods' Linux notes point the other way, towards disconnects.

**What it changes.** The identity every Bluetooth device sees from the laptop. It needs administrator rights and, going by NTPods' developer, a reboot; Microsoft's page does not say. Windows may need the AirPods removed and paired again, which is one pairing-mode double-tap and not a reset.

**Exact undo.**

1. Before changing anything, in an administrator terminal: `reg export "HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters" bthport-backup.reg`, and note which `DID` values already exist (usually none).
2. To undo, delete each `DID` value you added: `reg delete "HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters" /v DIDVendorID /f`, and the same for `DIDVendorIDSource`, `DIDProductID` and `DIDVersion` if you set them. If any existed before, run `reg import bthport-backup.reg` afterwards; an import restores old values but does not remove new ones, which is why the delete comes first.
3. Reboot. If the AirPods misbehave in Windows, remove them in Settings and pair them again.

## Route C: LibrePods on Linux, from a live USB now or a small board later

This route runs LibrePods' complete Rust code, takeover and audio included, so it needs no new code for Stage 2. It is the fallback if Route A stalls, and the same stack on a small board is the only design I found that gives the laptop the AirPods' microphone without a kernel driver. Plan and inference throughout, untested on your setup.

### C1. Live USB test (the plan's 2B), as the Stage 2 fallback

**What it changes on the laptop.** Nothing on the Windows disk. You boot Ubuntu from a USB stick through the one-time boot menu, without changing the boot order. Ubuntu's Microsoft-signed shim boots with Secure Boot on ([Ubuntu security docs](https://documentation.ubuntu.com/security/security-features/platform-protections/secure-boot/)). If your laptop refuses the stick with Secure Boot on, stop: getting past that would mean a Secure Boot setting change, which is ruled out. Have the BitLocker recovery key saved first anyway.

**The one real hazard: the built-in adapter.** LibrePods' Rust app uses BlueZ's default adapter, and bluer picks `hci0` when present ([bluer docs](https://docs.rs/bluer/0.17.4/bluer/struct.Session.html)), which on a laptop is usually the built-in radio. Pairing through it from Linux would replace the key Windows uses, so Windows would need to pair again. In the live session, take the built-in adapter offline for that session only (for example by writing 0 to its USB `authorized` file), then check that `bluetoothctl list` shows only the dongle's address before pairing anything. A reboot undoes it.

**What else it needs.** A USB stick with persistence or room to build, the Rust toolchain, and the `linux/rust` branch built locally. Its CI builds an AppImage, but only as a workflow artifact, so plan on building it yourself. Set `DeviceID = bluetooth:004C:0000:0000` in `/etc/bluetooth/main.conf` for the Apple-identity runs, as LibrePods' README says; on a live system that file vanishes at reboot.

**Undo.** Shut down and remove the stick. The AirPods keep a pairing record for the dongle, as in Route A.

### C2. A small Linux board as a USB headset (a Stage 3 design, listed so Stage 2 can inform it)

A Raspberry Pi 4 or Zero 2 W in USB gadget mode can present itself to Windows as a USB Audio 2.0 headset, which Windows drives with its own in-box driver. The board runs the same LibrePods stack as C1 with the spare dongle, so it holds the AirPods link and handles takeover, while the laptop just sees a sound card with speakers and a microphone.

- **For it.** Nothing installed on the laptop, no WinUSB binding, a working call microphone, and unplugging it is the whole undo.
- **Against it.** One more device to carry and power, added delay, and Windows' UAC2 support from a Linux gadget has mixed reports (one tester got no audio). LibrePods' takeover trigger watches local media players, so it would need changing to react to sound arriving over USB or to a button.
- **Why it matters now.** C1 and C2 share the AirPods-facing code, so a C1 pass is also evidence for C2. I found no one who has built this for AirPods multipoint.

## Ruled out on this laptop

Every route that puts third-party kernel code on the laptop is out, which removes the plan's Stage 2C and design A here; both stay possible on a spare PC.

| NTPods' driver (plan's 2C, design A) | Test-signed kernel driver: needs Test Mode and Secure Boot off | Hard constraints; [NTPods Windows README](https://github.com/arctumn/ntpods/blob/main/windows/README.md) |
| NTPods in a Windows VM with the dongle passed through | VirtualBox and VMware pass USB through with their own host kernel drivers | Hard constraint; inference about those products |
| MagicPods' driver | Needs Test Mode, and its multipoint is listed for counterfeit Airoha AirPods only | [MagicPods](https://github.com/steam3d/MagicPods-Windows), [MagicAAP](https://magicpods.app/magicaap/) |
| Virtual audio cable for Route A's sound or microphone | A third-party kernel audio driver, signed or not | Hard constraint |
| Apple's channel through Windows' own stack from an app (Tblob18, brianpht ports) | Microsoft supports RFCOMM sockets only, and NTPods recorded the L2CAP connect failing | [Microsoft sockets](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-socket); plan section 5 |
| Binding WinUSB to the built-in adapter | Windows would lose its only Bluetooth radio | [Microsoft Bluetooth FAQ](https://learn.microsoft.com/en-us/windows-hardware/drivers/bluetooth/bluetooth-faq) |
| Anything that resets the AirPods or changes their firmware | Hard constraint; firmware cannot be rolled back anyway | [Apple firmware page](https://support.apple.com/en-us/106340) |

## Stage 2 steps and gate

Stage 2 starts only if Stage 1 fails its gate, and then runs in two steps on Route A, with the live USB as the fallback if the dongle or Bumble is the problem rather than the AirPods.

A Stage 1 pass and every failed check end at the same place, manual switching with a one-key take and give back; only a working takeover reaches the Stage 3 design choice.

| Question | Pass | Stop |
| --- | --- | --- |
| Do both links hold? | iPhone and dongle both listed by the AirPods for 10 minutes, with at most one unexpected drop across the runs | Either host drops within minutes in most runs |
| Does the link survive the 9A348 drop? | No repeatable drop at 36 to 40 seconds, with or without the Apple identity | Repeatable 36 to 40 second drops with no workaround: spoofing is blocked on this firmware |
| Does a takeover move the audio? | 20 takeovers each way over two hours, at most one unexpected drop | The iPhone ignores the takeover, or it interrupts a call |
| Hard stop at any point |  | The iPhone pairing is disturbed, or anything prompts a reset |

The pass and stop lines reuse the plan's 2B criteria. Stage 3 starts only if both links held and a takeover worked on a path Windows can use, as the plan says.

**Prep that needs no change to the laptop.** Buy the dongle (about 10 to 15 euros) and check its ID on the box. The Route A script, timestamped logging plus the ported takeover messages, can be written and reviewed now and kept unrun until the gate.

## Untested on your setup, and open questions

No route here has been run on an iPhone, a Windows laptop and AirPods Pro 3 on 9A348 together, by me or by anyone I found. These are the specific gaps.

- **Bumble with AirPods Pro 3.** LibrePods' Windows script and airlow were developed against AirPods Pro 2. Pairing, Apple's channel and A2DP from Bumble to Pro 3 are untested.
- **Takeover from a non-Apple host on 9A348.** Whether the AirPods and your iPhone on current iOS honour "Hijackv2" from a non-Apple host. LibrePods reports the iPhone's banner appearing when Android takes over, but not for Pro 3 on 9A348, and not whether the iPhone takes the audio back on its own.
- **The 36 to 40 second drop outside Android.** Only reported from Android so far.
- **How many pairings the AirPods keep.** Apple does not document it. If the list is short, adding the dongle could push out an older pairing; the iPhone and Windows should be safe as recently used devices, but that is inference.
- **Binding details.** Whether Device Manager offers Microsoft's in-box WinUSB for the dongle, whether libusb opens it that way, and whether Windows Update ever puts the Bluetooth driver back (the dongle would reappear under "Bluetooth"; unplug it or bind again).
- **Keeping the built-in adapter out.** Whether switching Windows' Bluetooth off is needed, and enough, to stop it competing as a third host.
- **Live USB on this laptop.** Whether it boots Ubuntu with Secure Boot on; some machines ship with Microsoft's third-party certificate turned off, and that would end Route C1 here.
- **One-key reconnect rights.** ToothTray's code requests no administrator rights, but I did not run it.
- **Still open from the plan.** The three questions for NTPods' maintainer (which AirPods and firmware the August captures used, whether an Apple Device ID was set, and what happens on 9A348).
